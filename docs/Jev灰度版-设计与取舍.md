# Jev 灰度版：设计、实测结论与取舍

> **状态：实验装置已实装，默认关闭（`judge.engine = "rules"`），线上行为零变化。**
> 这份文档记录的是"评估一个判断模型要不要引入"的完整过程：量了哪两个位置、结论是什么、
> 为什么暂时不上线、以及面试/汇报时怎么讲。
> 相关代码：`rag/jev_client.py`、`rag/jev_judge.py`、`scripts/jev_shadow.py`。

---

## 1. 为什么会有这个东西

Jev 是 TypeSafe 出的**决策模型**：只回答**选择 / 打分 / 是非**，返回概率，**不生成文字**。
它最近受关注的原因是"**判断与生成分离**"——通用 LLM 做分类和路由又贵又不稳，
专用判断模型在窄任务上更省更准。

我的链路里有两个位置像"判断问题"，我**都量了**，而不是先接上再说。

---

## 2. 实测结论（这是全文最重要的部分）

### 2.1 位置一：「该不该答」→ **用数据否决**

`rag/judge.py` 用词表 + 正则判断"这条客户消息要不要回"。拿 600 条评测集
（`eval/messages_200{,b,c}.csv`，带 `期望行为` 标注）对比：

```
标注 auto       规则说要回 = 403    规则说不回 = 0
标注 escalate   规则说要回 = 163    规则说不回 = 0
标注 no_reply   规则说要回 = 0      规则说不回 = 34
判错 = 0 / 600   →  规则层 100%
```

那 34 条 `no_reply` 长这样：`好的` `谢谢` `嗯嗯` `？` `。。。` `😀` `666` `~~~`

**结论：这个位置是低熵问题（收尾语 / 表情 / 符号），正则已经满分，判断模型不可能更好。**
→ 否决 Jev 放在这里。顺带说明：这批判评测集**在这个维度上没有区分度**
（难度不足），不能用来验证判断模型。

### 2.2 位置二：「资料覆盖没覆盖」→ **真瓶颈，headroom 巨大**

现状用 **检索相似度 `top_score > 0.50`** 当"资料覆盖了没"的代理。
用 322 条标注干净的样本（大类「高频直答（资料库有答案）」→ 覆盖 196 条；
「资料缺口（应转人工）」→ 未覆盖 126 条）：

| 指标 | 现状（分数当代理） |
|---|---|
| 判对 | **234/322（72.7%）** |
| **假阳性**：说覆盖、其实没覆盖 | **87 条** |
| 假阴性：说没覆盖、其实覆盖（该答没答） | 1 条 |

假阳性的典型（`top_score` 都很高）：

| 客户消息 | top_score | 真实情况 |
|---|---|---|
| 现在店里有几台A7M4 | 0.653 | 实时库存，资料库不可能有 |
| A7M4 80一天行吗 | 0.728 | 议价 |
| 押金能不能少收点 | 0.706 | 议价 |
| 我的快递单号发我 | 0.528 | 订单物流 |
| 你们发错货了 | 0.542 | 售后纠纷 |
| 支持分期吗 | 0.532 | 未覆盖政策 |

**这是 RAG 最经典的失效模式：相似度不等于可答性（similarity ≠ answerability）。**
消息和资料库里的"库存说明""退换政策"语义高度相关，但资料里**没有那个事实**。

**它还解释了一个架构现象**：为什么我的护栏越加越多——因为上游"能不能答"的判断是错的
（72.7%），所有"不该答"的情况只能堆到下游用词表兜。**把 Jev 放在这里，是把兜底前置。**

完整基线报告：`docs/Jev对比-资料覆盖基线.md`（`scripts/jev_shadow.py` 生成）。

## 3. 设计：只换一个点，而且它只有否决权

### 3.1 三态引擎（`config.json` → `judge.engine`）

| engine | 行为 | 用途 | 风险 |
|---|---|---|---|
| `rules`（默认） | 完全走 `rag/judge.py`，不联网 | 线上现状 | 无 |
| `shadow` | **规则决定行为**，同时问一次 Jev，只落 `logs/jev_shadow.jsonl` | 取证：攒对比数据 | 零（不改行为） |
| `jev` | **Jev 决定**，失败/超时/没 key → 自动退回规则层 | 灰度 | 低（见下） |

### 3.2 硬约束：Jev 只有否决权，没有放行权

```
Jev 说"不必回" → 不回（它拦下来了）
Jev 说"要回"   → 仍然要过检索 / 护栏 / 阈值这三关才能发出去
```

**它永远不能凭一句话让回复发给客户。** 这样即使判断模型判错，最坏结果也只是
"少答一条、转人工"，不会多发给客户——**判错方向不对称时，只给否决权是唯一安全的接法**。

### 3.3 分级调用（保护延迟与成本）

判断约 1 秒、约 1000 输入 token。**每条都问会把 1.5 秒的中位响应拉到 2.5 秒**，
所以默认 `ask_when = rules_say_reply`：只在规则层说"要回"时才问
（规则说不用回的本就不生成，没必要花钱判断）。

### 3.4 题目按客服语域重写（不能照抄）

Jev 聊天助手自带的 8 道题是**社交语域**（QQ/X/飞书、恋人/朋友/同事/家人、群聊不准），
**照抄到客服必错**。我按客服语域写了 4 道（`rag/jev_judge.py` 的 `QUESTIONS`）：

| 题目 | 类型 | 用途 |
|---|---|---|
| `is_actionable_question` | 是非(noul) | 位置一的决策题：这条要不要回 |
| `message_intent` | 单选 | 问价/问库存/问规则/问时间地点/闲聊/骚扰/无效（同一请求里顺手带的证据） |
| `needs_human_authority` | 是非(noul) | 是否只有店主能定（议价/投诉/退款/合同） |
| `kb_covers_question` | 是非(noul) | **位置二的决策题**：给它的检索片段有没有答上这个问题 |

三条硬规则（照 Jev 官方要求）：**instructions/criteria 一律英文**（中文只留在 state 的
聊天原文里）、**一次请求带全部题目**（加题不加价）、**题目之间不许互相矛盾**。

## 4. 好处（具体到数字）

| 好处 | 说明 |
|---|---|
| 从"代理"换成"显式判断" | 现状用相似度当可答性的代理，实测只有 72.7%；显式判断才对症 |
| **省一次生成** | 判"资料不覆盖"的直接转人工，不必走 LLM（省 token、省 1~2 秒） |
| 补词表的死穴 | 词表"换个说法就漏"（实测过 19 条危险直发里有一部分是这个原因） |
| 概率可直接用 | 判断返回概率，不必像现在这样用检索分硬凑置信度 |
| 判断比生成便宜一个量级 | 一次判断约 1000 输入 token；博查 Jev 现在限时免费 |
| 口径可校准 | 题目显式 + 已有 322 条干净标注，能算准确率；改正则没有这种闭环 |
| 天然有降级路径 | 判断失败 → 退回规则层（判断层不能成为接待的单点故障） |

## 5. 风险（按严重程度）

### 5.1 隐私：多一个固定的第三方端点
现状口径是"**对话不出本机**，只把'客户这一句话 + 命中片段'发给店主**自己配的**接口"。
接 Jev 意味着**每条客户消息都要发到 TypeSafe / 博查 / OpenRouter 之一**。
店主会问"我客户的消息发给谁了"。→ 解法：让店主自备 key（他付钱他知情），或只在灰度/影子跑。

### 5.2 延迟 +1 秒
必须用分级调用压住（见 §3.3），否则中位响应从 1.5 秒退化到 2.5 秒。

### 5.3 成本结构变了
规则层是 0 成本；判断每条都要花钱。¥12/月 的口径要重算（判断可能比生成便宜，
但**次数多**）。

### 5.4 可解释性与调优速度下降
现在"该不该答"由词表决定：可解释、可审计、**改一行即时生效**。换模型后不达标只能
**改题目措辞重跑**（Jev 官方做法是"最多 3 轮"），调优从**分钟级变小时级**。

### 5.5 阈值不会消失
Jev 给概率，还是要定"概率 > 多少才覆盖"。**不是"换了就不用定阈值"，只是换了对象。**

### 5.6 判断与生成会打架
Jev 自己踩过两题矛盾（`should_answer_now` 0.77 vs `best_action` 0.60）。
所以三类落地校验 + 越权承诺 + 拖延话术护栏**一条都不能删**，只能变第二道。

### 5.7 模型会漂移
`typesafe/jev-1.13` 与 `jev-latest` 是两个东西；版本升级后行为可能变。
所以它必须和评测集绑定，能随时复跑。

## 6. 为什么现在暂不实装（六条，都能被追问）

1. **只有基线，还没有对照**：目前量的是"现状 72.7%"，**Jev 那一列还是空的**——
   还没有 key 去跑。**没有对照就不能说它更好。**
2. **题目没经过校准**：题目刚写、没有按 Jev 的脚手架做标注集校准（打分题 MAE、
   选择题命中率、不达标改措辞重跑）。**没校准的题目不该碰客户。**
3. **隐私口径未与业务方确认**：每条客户消息外发到新端点，需要店主明确知情同意。
4. **判错方向不对称**：判"覆盖"其实没覆盖 → 会拿错资料答（说错话、不可逆）。
   必须先在影子模式攒够证据。
5. **延迟与成本要重算**：+1 秒、每条一次判断，会影响"月成本 ≈¥12"这个承诺。
6. **它不是当前最紧的事**：600 条里那 30 条"该答没答"的根因有三处
   （检索分/模型自己要人工/拖延护栏误拦），判断层只能解决其中一部分。

**正确的推进顺序**：影子模式跑一段 → 用 322 条标注集证明 Jev 打过 72.7% →
灰度（只在自己号上）→ 再用同一套尺子（46 题 + 3×200 条）复核不退化 → 才谈上线。

**验收线**（用我的数据重定，比 Jev 原版的 60% 严）：判断命中率 **≥ 70%**，
且**危险直发仍为 0**。

## 7. 前置：怎么拿到 Jev 的 key

⚠️ **Jev 不在博查开放平台（open.bocha.cn）那 4 个 API 卡片里**（那里是 Web Search / Model / Agent Search / Semantic Reranker）。
Jev 是个**独立站点** `https://jev.bocha.cn`（一个决策模型 Playground，用模型玩马里奥/魂斗罗那种），
接口是 `POST https://jev.bocha.cn/v1/systemone`，模型 `bocha-jev-v1`。

凭据变量名（**官方 SKILL.md 的规定，按优先级**）：

    首选 BOCHA_JEV_API_KEY
    其次 BOCHA_SEARCH_API_KEY     ← "已有博查 key 且有权访问该服务时可复用"
    兼容 JEV_API_KEY              ← Jev 聊天助手那个客户端用的名字

> `JEV_UPSTREAM_API_KEY` 是**服务端内部凭据**，不是给客户端用的，别填错。

**拿 key 的步骤**：
1. 先在 open.bocha.cn 点「**点击免费领取 1000 次调用资源包**」（你截图里资源包是 0 个）
2. 左侧「**API KEY 管理**」→ 新建/复制一把 key
3. 把这把 key 填进项目根目录 `.env`（`BOCHA_JEV_API_KEY=xxx`），跑 `--ping` 验证
4. **401 的话**说明这把 key 没有 Jev 权限 —— 去 `https://jev.bocha.cn` 领限时免费的，
   或看接口文档（飞书）：https://bocha-ai.feishu.cn/wiki/PhrPwCrEaiCyyPkkDNecdfRSnHR
5. 备用来源：OpenCode Zen（`JEV_PROVIDER=opencode`，模型 `jev-1.13-free` 限时免费）；
   要稳定就 OpenRouter / TypeSafe 直连（付费）

**已验证**：拿一把假 key 打过去返回的是 **HTTP 401**（不是 404/422），
说明**地址与协议正确、端点可达**，只差有效凭据。
## 7. 怎么跑（一条命令）

```bash
# 1) 不联网：先量现状基线（已跑过，见 docs/Jev对比-资料覆盖基线.md）
python scripts/jev_shadow.py --dimension coverage --dry-run

# 2) 先在 .env 里配凭据（官方名 BOCHA_JEV_API_KEY，见 §7.1）后先跑 30 条
python scripts/jev_shadow.py --dimension coverage --limit 30

# 3) 全量 322 条，出报告
python scripts/jev_shadow.py --dimension coverage --out docs/Jev对比-资料覆盖.md

# 4) 换引擎（灰度/影子）只需改 config.json：
#    "judge": {"engine": "shadow"}   ← 影子：不改行为，只落 logs/jev_shadow.jsonl
#    "judge": {"engine": "jev"}      ← 灰度：Jev 决定（只有否决权）
```

## 8. 面试/汇报话术（3 分钟版）

> "最近 Jev 这个判断模型挺受关注，它的思路是'判断与生成分离'——只回答选择题和打分、
> 返回概率、不生成文字。我评估过要不要用它替换我的规则判断层，**量了两个位置**。
>
> 第一个是'该不该答'。我的规则层在 600 条标注集上是 **100%**，判断模型反而更低——
> 因为这是低熵问题（收尾语、表情、符号），正则就够。**所以我把这个方案否决了。**
> 顺带说，这批判评测集在这个维度上没有区分度，也说明**不是所有判断都值得上模型**。
>
> 第二个是'检索到的资料到底覆没覆盖客户的问题'。这是 RAG 的经典失效模式——
> **相似度不等于可答性**。我量了 322 条干净标注：现状用相似度分数判断，**只有 72.7% 正确，
> 87 条把'其实没覆盖'判成了'覆盖'**。这些'不该答'全靠下游词表兜——**这就是我的护栏
> 越加越多的根本原因**。我给它带上检索片段，让 Jev 直接判覆盖，**这才是判断模型该在的位置**。
>
> 我**没有直接上线**，三个原因：一是我还没跑出 Jev 的对照数，**没有对照就不能说它更好**；
> 二是它会引入一个固定的第三方端点，和我'对话不出本机'的口径冲突；三是判错方向不对称——
> 判'覆盖'其实没覆盖会拿错资料答，不可逆。
>
> 所以我给它只留了**否决权**：它说'不必回'就拦下，说'要回'仍然要过检索、护栏、阈值三关。
> 推进顺序是**影子模式 → 证明打过 72.7% → 灰度 → 同一套尺子复核**。
> **先证明它更好，再让它碰客户。**"

**这段为什么强**：它同时展示了四件事——懂新技术（能讲清 Jev 的机制）、会量化（两个维度都有数）、
敢否决（100% 那个位置直接否）、有边界感（只给否决权、验收线、推进顺序）。
比"我在项目里用了 Jev"高一个档。

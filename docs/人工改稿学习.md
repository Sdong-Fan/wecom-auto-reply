# 从人工改稿里学习（语气自动学，事实要确认）

对应代码：`rag/learn.py`（分析 + 写入）、`rag/learn_store.py`（存/去重/遮蔽/上限）、
`gui/learn_dialog.py`（勾选窗）、`main.py`（发送成功后触发）、
`gui/kb_dialog.py` 的「学到的」页。

## 触发点：发送**成功**之后 → 弹窗勾选 → 确认才写

```
待人工页 → 编辑 → _handle_pending_edit
   → send_queue.put(("send", 客户, 终稿, {客户原话, AI草稿}))   ← 第 4 项是学习上下文
   → _process_send_queue_tick → _do_send → send_ok
   → if send_ok: _learn_from_edit(...)                        ← 只有真发出去才学
   → 后台线程 propose()（只分析，不写库）
   → root.after(0) 弹勾选窗
   → 用户勾完点确认 → 后台线程 commit()（写库）／点取消 → 什么都不写
```

三个要点：

* **挂在 `send_ok` 上**：`_do_send` 会因为"没能确认当前打开的是这个客户的会话"而拒绝发送
  （防发错人）。没发出去的话不该被学走。
* **propose / commit 分开**：分析完**先不写**，等用户在勾选窗里勾。这是硬边界 ——
  测试里专门有一条 `test_propose_writes_nothing` 盯着"没确认之前库里一个字都不能多"。
* **异步**：分析要调 LLM（几秒），写入要跑嵌入（几秒），都放后台线程；
  弹窗必须回 Tk 线程（`root.after(0, ...)`）。同一时刻只开一个勾选窗，
  后面的候选排队等（`_learn_state`）。

## 勾选窗（`gui/learn_dialog.py`）

```
┌ 这次对话
│ 客户问：周末发货吗
│ AI 草稿：您好，关于发货时间的问题，我这边需要为您确认一下。
│ 你发出去：周末也发的，下午三点前的单当天就走
├─────────────────────────────────────────────
│ 语气习惯（以后所有回复都按这个说话）
│   [x] 直接给结论，不客套，短句为主
│ 口吻样本（以后照着这句话的味道说）
│   [x] 周末也发的，下午三点前的单当天就走
│ 新说法（会写进资料库，以后按这个回答客户）    ← 红字提醒"写错就是报错价"
│   [x] 周末也发货      客户问「周末发货吗」→ 回答这句
├─────────────────────────────────────────────
│                        [取消不学习] [确认学习选中的]
```

* 默认**全勾**，不想学的自己去点掉
* 已经学过的会标"（已经学过）"，重复勾也不会重复占位（去重 + 命中计数）
* **点「取消」＝这次什么都不学**（不是"稍后再说"）。关掉窗口（X）等同于取消
* 勾中的新说法**直接写进资料库**（走 `kb_tools.add_entry` + `kb_history`，可撤销）；
  未勾的丢弃。入库失败时退回「待确认」列表，不会悄悄丢

## 三分法（整个设计的核心）

| 学什么 | 例子 | 处理 |
|---|---|---|
| 语气/措辞 | "您好，我为您查询一下" → "我看看哈" | 自动学，追加进提示词 |
| 事实/资料 | 人工补了"周末也发货"、"专票普票都行" | **必须勾选确认**才进资料库 |
| 绝不学 | "这次给你免押"这种一次性例外 | 靠勾选拦下来 |

自动学语气安全（只改措辞不改事实）；自动学事实危险 —— 一次性例外会变成通用政策。
所以两条路完全分开，而且都要过勾选这一关。

**两个不学**：

* 直接点「发送」（没编辑）→ **不学语气**，只记采纳次数 + 把「客户问题 + 发出的回答」
  当成**待确认的问答对**收进「学到的」（见下节）。
* 草稿和终稿归一化后一样（只改了标点和空格）→ 不学。

## 直发确认（待人工页直接点「发送」）

店主点了「发送」＝ 用行动认可了这个回答。这时候没有"改稿"可比，所以不学语气，
而是把**问答对**收进「学到的」待确认：

```
客户问「有打算在鼓浪屿开分店吗」
→ 回答「目前在琢磨，还没定。你要是有需求可以先跟我说，我记着。」
来源：直发确认
```

点「采纳进资料库」→ 立刻成为一条资料 → **下次同一个问题检索分就高了，不用再转人工**。
这是最省事的补资料入口：不用自己想问题该怎么写，直接拿客户的原话。

* 「学到的」页的**来源**列标着是「直发确认」还是「改稿学到」
* 同样只在**发送成功之后**才收录（发失败不算认可）
* 空回答、太短的不收；重复直发同一条只累加命中次数
* **不写语气样本** —— 拿 AI 自己写的话当口吻样本等于让机器人学自己

## 怎么分离语气和事实

一次 LLM 调用（`analyze`），输入 客户原话 + AI 草稿 + 人工终稿，输出：

```json
{"style_rules": ["省略客套，直接报信息"], "tone_sample": "在的在的，你说哪台",
 "facts": ["周末也发货"]}
```

**没网/没配 key 时走规则兜底**（`fallback`）：终稿里有草稿和原话都没有的数字 → 当新事实
交人工确认；其余当语气样本。兜底的固有损失是**抓不到不带数字的新说法**
（"周末也发货"），这一点不装作学到了。

## 遮蔽：学来的句子会进提示词，所以数字必须遮

出厂样本里就有 `押金 4000，还回来就退你，放心`。这种句子被注入提示词后，
模型可能把 4000 抄到别的回答里（guard 会拦下 → 转人工，不至于报错价，
但白折腾一轮）。所以学来的样本把**独立整数**换成 ▢：

- `押金 4000，还回来就退你` → `押金 ▢，还回来就退你`
- `A7M4 明天还剩一台` → 不变（型号里的数字不是价格，遮了反而看不懂）

顺带遮手机号和 `@昵称`。客户名根本不落库（只存内容 hash），避免"这个客户说过什么"被记下来。

## 规则去重：**余弦不可靠，用 LLM 归并**

一开始想用本地 BGE 算语义相似度合并规则，实测数据否掉了这个方案：

| 关系 | 余弦 |
|---|---|
| 同一件事（"短句为主，语气直接" vs "省略主语和客套话，直接报信息"） | 0.68 |
| 不相干（"报价前先问客户拍什么" vs "称呼用你不用您"） | 0.53 |

区间重叠，阈值分不开。所以：

* `similar_rule` 只拦**几乎逐字相同**的（阈值 0.82，便宜的兜底）
* 主力是 `consolidate()`：规则超过 6 条时让 LLM 归并成 ≤6 条互不重复的。
  **天然限流** —— 归并后一定 ≤6，要重新长到 7 条以上才会再调一次 LLM。

实测 5 次改稿：不归并会攒出 10 条高度重叠的规则，归并后稳定在 6 条
（"直接给结论，不客套，短句为主" 这种把三条并成一条）。注入名额只有 8 个，
不归并的话很快就被同一件事占满，真正不同的习惯挤不进去。

归并后用 `order` 字段记住"哪条更重要"（顺序＝归并输出顺序），`hits` 重置为 1
（归并后没法对应回原条目，次数只用于排序，不影响功能）。

## 注入：追加，不写进用户的提示词文件

`learned_block()` 生成一段，`append_to_system()` 追加到 system 提示词尾部 ——
业务回复（`build_prompt`）和闲聊（`generate_smalltalk_reply`）两条路都追加。

为什么不写进 `prompts/system.md`：那是用户可编辑的文件，程序往里写会覆盖用户改动、
"恢复默认"也会变得莫名其妙。追加式还有个好处：用户能在「学到的」页点
**「预览实际注入给 AI 的内容」**，看见 AI 到底学到了什么 —— 学偏了能一眼看出来。

注入上限：6 条规则 + 5 条口吻样本 + 3 组改稿对照。改稿对照（`草稿 → 终稿`）
比孤立句子更能教会模型"该怎么改"。

## 开关

`config.json` → `kb.learn`：

```json
{"enabled": true, "max_items": 50}
```

`enabled=false` 时**既不学也不注入**。注意 `rag/generator.py` 生成回复时手上没有
内存里的 config，所以 `learn_store.enabled(None)` 会按 mtime 缓存地读 `config.json`
—— 否则界面上关掉了、实际还在学，那是骗人。

## 「学到的」页

| 区域 | 作用 |
|---|---|
| 待确认的新说法 | 勾选窗里**入库失败**时退回到这里；也可手动**采纳进资料库**（走 `kb_tools.add_entry` + `kb_history`，可撤销）/ 丢弃 |
| 已学到的语气 | 规则 + 口吻样本，可「删掉这条」或「这条别学」（进黑名单，不再学回来） |
| 预览实际注入给 AI 的内容 | 透明 |
| 自动学习 | 总开关，写回 config.json |

采纳进资料库跑在后台线程（嵌入是本机 CPU 跑的，主线程会假死）。

## 附：待人工「一条消息一行」

**首版做反了**：店主说"待人工同一人的消息不叠加"，我理解成"同一个人只留一条
（新的顶掉旧的）"，还顺手把 OCR 名字变体也归并了 —— 结果是他问
「有打算在鼓浪屿开店吗」+「鼓浪屿房租不便宜」，第二条把第一条**顶没了**，
他只看得到一条。他要的恰恰相反：**两条不同的问题 = 两条待人工**。

现在的规则：

| 情况 | 结果 |
|---|---|
| 同一个人问了两件不同的事 | **两条**，各处理各的 |
| 同一条消息重复入队（发送失败重试、标点抖动） | 合成一条，不刷屏 |
| 同一个人的 OCR 名字变体（`@微信` 读不出来、名字粘着预览） | 归一到**同一个人**，不产生假的人 |
| 一个人攒超过 `DEFAULT_MAX_PER_CUSTOMER`(10) 条 | 丢最旧的（防刷屏的保险丝；阈值留足余量，挤掉问题正是要修的毛病） |

实现要点：

* key = ``人::消息指纹``（消息指纹归一掉空白和标点）。界面那一行用 key 定位 ——
  用客户名的话，同一个人的两行点哪行都一样
* `person` 是内部标识（第一次见到的写法），用来把人分组；`customer_name` 留
  **最干净的那个写法**（发送时要用它对会话）
* `get/remove/mark_expired` 按人（兼容老调用，取最新一条）；
  界面走 `get_key/remove_key`
* 老文件（一人一条、key 就是人名）读回来时按「人+消息」补出 key，不用迁移

## 附：待人工「同一个人的消息不叠加」

这个问题和改稿学习无关，但一起修了。根因在**会话名的读法**：

OCR 读出来的会话名经常是 **「名字 + 消息预览」**：

```
客户A@微信                        ← 干净
客户A@微信 帮您问下算好没，稍等。      ← 带预览
客户A 这一串我算不明白了             ← @微信 没读出来，后缀切不断
```

`clean_name_text` 靠 `@微信` 后缀切断预览。**后缀没读出来时，预览整串会留下**，
消息一变就是一个新 key —— 同一个人就摞成好几条待人工（真实日志里
`客户A` 不带后缀出现过 79 次）。而且 Key 不同还会导致"发送目标"对不上。

修法：`PendingQueue.push` 先把名字**归一到同一个人的已有 key**（`name_candidates`
列出「整串 / @ 之前 / 第一个空格之前」三种写法，用**完全相等**比对）。
`get` / `remove` / `mark_expired` 也走同一套归一，界面拿 `item.customer_name` 也找得到。

为什么用**完全相等**而不是模糊相似度：归一错了就是把 A 的回复发到 B 那里 ——
宁可漏归一（同一个人偶尔还是两条），也不能把两个人合成一个
（`test_different_people_are_not_merged` 盯着这条）。归一时保留更干净的那个名字
（更短的通常是不带预览的），发送要用它。

## 已知局限

* 从**一个人**的改稿里学通用口吻，样本少时容易学偏。对策：只学措辞层面、
  给规则加命中计数、上限 6 条、每条可删、有总开关、能预览注入内容。
* 归并要额外一次 LLM 调用（只在规则从 ≤6 长到 >6 时发生，不是每次改稿）。
* 学习线程里 `asyncio.run` 复用全局 AsyncOpenAI client，跨事件循环偶发失败时
  会退化成规则兜底（不会影响发送）。

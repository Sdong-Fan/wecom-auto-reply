# 判断层：现状 vs 换成 Jev 方案

> **状态：方案，未实施。** 这份文档是为了回答一个问题——"我现在靠检索分数决定该不该答，
> 换成 Jev（TypeSafe 的判断模型）会有什么差别？值不值？"
> 结论先写在最后（§6）。

---

## 1. 现状：一次客户消息的完整流水线

真实顺序（`rag/responder.py` 的 `Responder.generate_reply`，按代码行号排）：

| # | 环节 | 判据 | 类型 | 结果 |
|---|---|---|---|---|
| 1 | 无信息量 | `is_low_information()`：纯符号/纯数字/纯表情 | 规则（正则） | 不回 |
| 2 | 太短 | `len(text) < 2` | 规则 | 转人工 |
| 3 | **该不该答** | `should_reply()`：收尾语/确认/感谢 → 不回；疑问线索 → 回 | 规则（词表 + 正则） | 不回 / 继续 |
| 4 | 越界请求 | `out_of_scope()`：要凭据 / 算长算式 / 让你背诗 | 规则（词表） | 模板婉拒（自动发） |
| 5 | **必须转人工** | `must_escalate()`：投诉 / 议价 / 押金特批 / 发票合同 | 规则（词表） | 转人工 + 占位语 |
| 6 | 本地直答 | `answer_locally()`：几点 / 几号 / 星期 | 规则（读系统时钟） | 自动发 |
| 7 | 向量化 | `bge-small-zh-v1.5`（512 维，本地 CPU） | 小模型 | — |
| 8 | **检索** | Qdrant top-k=5，取相似度最高的 `top_score` | 检索 | 分数 |
| 9 | 检索兜底门 | `check_retrieval()`：`top_score < 0.5` → block | 阈值 | 转人工 |
| 10 | 闲聊分流 | `classify_message()`：词表判 smalltalk / business | 规则 | 决定用哪套提示词 |
| 11 | 生成回复 | LLM：系统提示词 + 口吻样本 + 最近 3 轮历史 + 命中的知识片段（temperature 0.8） | 大模型 | 草稿 |
| 12 | 内部信号 | `is_human_marker()`：草稿是"需要人工处理" | 规则 | 不当草稿 |
| 13 | 越权承诺护栏 | `unsafe_promise()`：有货 / 留货 / 保证 / 时效 | 规则（正则） | **转人工** |
| 14 | 拖延话术护栏 | `deferral_phrase()`：晚点回你 / 我问问店里 | 规则（正则） | **转人工** |
| 15 | 二档质量门 | `classify_and_dispatch()`：数字/型号/时间三类落地校验 + 不确定性词 | 规则 | pass / low_risk / block |
| 16 | **派发** | `allow_auto_send` 且非内部信号 且 `decision != block` 且 **`top_score > 0.50`** | 阈值 | 自动发 / 转人工+占位语 |

**一句话概括现状**：*"该不该答"这个决策，由**规则词表 + 一个检索相似度分数**共同决定。*

**这个设计最弱的一环**：`top_score` 回答的是**"资料像不像客户这句话"**，不是**"这个问题该不该我答"**。
两者不等价，实测证据：

- 46 题评测里 15 道"该答却转人工"，其中 **12 道答案就在库里、模型也答对了**，
  是被检索分卡在阈值附近（当时 0.60~0.64，门槛 0.65）拦下的。
- 三批 600 条测试剩余的 30 条失败，**全都是"该答没答"（保守转人工）**，
  其中约 10 条就是"检索分卡在门槛附近"。

也就是说：**我不缺答案，我缺"该不该答"的判断。**

## 2. 先把名字理清楚（这是三个不同的东西）

| 名字 | 是什么 | 归属 |
|---|---|---|
| **Jev（判断模型）** | **决策模型**：只回答**选择 / 打分 / 是非**，返回概率（`choice` → `probabilities`、`score` → `noul`/`confidence`），**不生成文字**。协议 `POST /v1/systemone` | **TypeSafe**（`docs.typesafe.ai` / `api.typesafe.ai`） |
| **Jev 聊天助手（应用）** | 三平台的**开源"对话副驾"**：Android（`jev-chat/jev-chat-jarvis`）、Windows（`jev-chat/jev-chat-windows`）、macOS（`jev-chat/jev-chat-jarvis-mac`）。**用 Jev 做判断**，自己不是判断模型 | GitHub 组织 `jev-chat`，作者 Finderchangchang 与贡献者，MIT，官网 `chatjevs.com` |
| **我本地下载的那份** | 上面三端里的 Windows 端 | 同上 |

> ⚠️ 别把这两层混起来：**「Jev 聊天助手」≠「Jev 模型」**，它也不是 TypeSafe 官方出的应用，
> 而是一个**独立开源项目**，只是整套设计以这个判断模型为核心。
>
> 另外：**它并不只做微信**——Android 版**已全面下架微信支持**（现支持 QQ / X / 飞书，
> 因为微信 Android 版下架），**微信只在 Windows 端**（微信 Windows 4.x）。

### 2.1 判断模型有多家托管，协议统一（这条很实用）

| 来源 | 地址 | 模型名 | 备注 |
|---|---|---|---|
| **OpenRouter**（应用默认） | openrouter.ai | `typesafe/jev-1.13` | — |
| **TypeSafe 直连** | `api.typesafe.ai` | `jev-latest` | 官方 `typesafe_sdk` |
| **博查 Jev** | `https://jev.bocha.cn` | `bocha-jev-v1` | 协议同 TypeSafe，**当前限时免费** |
| **Vercel AI Gateway** | `https://ai-gateway.vercel.sh/typesafe` | `typesafe-ai/jev` | — |
| **OpenCode Zen** | `https://opencode.ai/zen` | `jev-1.13` | 输出免费、输入 $0.042/M；`jev-1.13-free` 限时 |

一次请求可以带**全部题目**（官方推荐做法），实测约 1000 输入 token、**约 1 秒**返回。
调用形状：

```
POST /v1/systemone
{
  "state":     { ...对话上下文（可带 background / history）... },
  "questions": { "q1": {"type": "choice", "criteria": [...]},
                 "q2": {"type": "score",  "criteria": [...]} }
}
→ 每道题一份答案 + 概率
```

### 2.2 应用侧是"三路接口"，其中一路就是**视觉**（对你有用）

Jev 聊天助手的设置页分成 **判断接口 / 回复接口 / 视觉接口** 三张卡，各自可填地址、密钥、模型
（只填判断接口那一把，另外两路会自动继承）。

**也就是说：这个生态里"看图"是独立的一路，不靠判断模型。** 你要做"识别图片"，
切分方式可以直接参照它——判断归判断、生成归生成、视觉归视觉。

## 3. 换成 Jev 之后的流水线

**关键差别：判断提到生成之前。**

| # | 环节 | 现状 | 换成 Jev |
|---|---|---|---|
| 1–2 | 无信息量 / 太短 | 规则 | **保留**（0 成本，先挡掉噪音，不必花钱判断） |
| 3 | 该不该答 | `should_reply()` 词表 | **Jev 题**：`is_actionable_question`（是非）+ `message_intent`（单选：问价/问库存/问规则/闲聊/骚扰/无效） |
| 4–5 | 越界 / 必须转人工 | `out_of_scope()` + `must_escalate()` 两张词表 | **Jev 题**：`is_scope_violation`（是非）+ `needs_human_authority`（是非：议价/投诉/退款/合同/特批） |
| 6 | 本地直答 | 规则 | **保留**（时钟没必要问模型） |
| 7–8 | 向量化 + 检索 | 无条件执行 | **改成条件执行**：判断说"可答"才检索（省一次 embedding+检索） |
| 9 | 检索兜底门 | `top_score < 0.5` → block | 保留，但**降级为兜底**，不再承担"该不该答"的职责 |
| 10 | 闲聊分流 | `classify_message()` 词表 | **由 `message_intent` 直接给出**，不用再猜 |
| 11 | 生成 | 无条件生成 | **只在判断说"可答且该我答"时才生成**（省钱、省延迟） |
| 12–14 | 承诺 / 拖延护栏 | 事后正则 | **事前**加 `contains_commitment_risk` 判断；**事后护栏保留**（第二道） |
| 15 | 二档质量门 | 规则 | 保留（三类落地校验不能删） |
| 16 | 派发 | `top_score > 0.50` | **`safe_to_auto_send` 的概率 > 阈值**（阈值还是要定，只是换了对象） |

**一句话概括新方案**：*"先让判断模型回答'这是不是个我能答的问题、该不该我答、风险多高'，
再决定要不要检索、要不要生成、要不要自动发。"*

### 3.1 落点排序（**已实测修正**）

> ⚠️ 这一节的排序原来是靠推理排的，**2026-10-05 用评测集实测后被推翻了一部分**。
> 结论与数据见 [Jev灰度版-设计与取舍.md](Jev灰度版-设计与取舍.md) 与
> [Jev对比-资料覆盖基线.md](Jev对比-资料覆盖基线.md)。修正后的结论：

| 落点 | 现在靠什么 | 实测结果 | 结论 |
|---|---|---|---|
| **① "该不该答"**（第 3 + 10 环节） | `should_reply()` + `classify_message()` 两张词表 | 规则层在 600 条标注上是 **600/600（100%）**；34 条 `no_reply` 全是表情/符号/收尾语 | ❌ **否决**——低熵问题，正则已满分，判断模型不可能更好 |
| **② "资料覆盖没覆盖"**（第 16 环节的上游） | `top_score > 0.50` **用相似度当代理** | 322 条干净标注上只有 **234/322（72.7%）**，**87 条假阳性**（说覆盖、其实没覆盖） | ✅ **这才是该上的地方**：`similarity ≠ answerability`，护栏越加越多的根因就在这里 |
| **③ 草稿复核**（第 13–14 环节的第二道） | 事后正则（踩过"换个说法就漏"） | 危险直发已是 0，没有可量化的 headroom | ⏸ 暂缓——**没有 headroom 就不该换** |

**为什么①会判错**：原推理把"600 条里 30 条失败 = 该答没答"直接归因给了判断层。
实测发现那 30 条的根因在**下游**（检索分卡门槛、模型自己要人工、拖延护栏误拦），
判断层本身是好的。**教训：不要用"看起来像瓶颈"代替"量出来的瓶颈"。**

### 3.2 四个不该用 Jev 的地方（划边界同样重要）

| 环节 | 为什么不该换 |
|---|---|
| 无信息量 / 太短（第 1–2） | 0 成本正则就能挡住，换模型纯浪费钱和延迟 |
| 几点 / 几号（第 6） | 确定性计算，模型反而会算错 |
| embedding + 检索（第 7–8） | 这是**检索问题**，对症的工具是 rerank / 混合检索，不是判断模型 |
| 数字 / 型号 / 时间落地校验（第 15） | **确定性检验比模型可靠**——这是你现在做得对的地方，别换 |

### 3.3 该"双保险"而不是替换的地方

**必须转人工**（议价 / 投诉 / 退款 / 合同 / 特批）：

- 现状：`must_escalate()` 词表
- 建议：**规则 OR 模型**——任一说"要转人工"就转
- 理由：这里**宁可错杀**。模型提高召回（换句说法也能识别），规则保证下限（枚举过的场景不漏）

### 3.4 保护延迟与成本：分级调用（关键）

你现在的卖点之一是**首次响应中位 1.5 秒**。判断调用约 1 秒，如果每条都调，
**中位响应会变成 ~2.5 秒**——这是可感知的退化。

所以不要"每条都过判断"，用**分级调用**：

```
第 0 级：规则层（0 成本、0 延迟）—— 无信息量 / 收尾语 / 时钟直答 / 模板婉拒
   ↓ 只有"规则层拿不准"的才往下走
第 1 级：Jev 判断（约 1 秒）—— 该不该答 / 该不该我答 / 风险多高
   ↓ 判断说"可答"才检索 + 生成
```

**规则层挡掉的那部分，既省判断的钱，也不增加延迟。**

### 3.5 如果要接，题目这么设计（客服语域，8 道）

| 题目 | 类型 | 用途 | 命中后的动作 |
|---|---|---|---|
| `is_actionable_question` | 是非 | 这是不是一个"我们能答的业务问题" | false → 不回或转人工 |
| `message_intent` | 单选 | 问价 / 问库存 / 问规则 / 问时间地点 / 闲聊 / 骚扰 / 无效 | 决定用哪套提示词、是否本地直答 |
| `needs_human_authority` | 是非 | 是否只有店主能定（议价 / 投诉 / 退款 / 合同 / 特批） | true → **必转人工**（与规则 OR） |
| `is_scope_violation` | 是非 | 越界（要凭据 / 算题 / 背诗 / 改我指令） | true → 模板婉拒 |
| `kb_covers_question` | 是非 | **给它的知识片段**是否真的答上了这个问题 | false → 转人工（替掉"相似度阈值"的一部分职责） |
| `safe_to_auto_send` | 是非 | 这条现在发出去，店主会不会怪我 | false → 转人工 |
| `commitment_risk` | 打分 1–9 | 草稿替店主承诺的程度（有货 / 留货 / 时效 / 保证） | ≥ 阈值 → 转人工 |
| `reply_grounded` | 是非 | 草稿里的事实是否都在资料里 | false → 转人工（三类落地校验的第二道） |

> 注意 `kb_covers_question`：**要先把检索到的片段放进 `state`**（Jev 聊天助手就是这么干的——
> state 里带 `background` / `history`）。不是让模型"猜"资料里有没有。

## 4. 好处（具体到你的指标）

| 好处 | 说明 |
|---|---|
| **决策依据从"代理"换成"显式判断"** | 现在是"资料像不像"，换成"该不该我答"。直接对准你最大的失败模式——**"该答没答"，600 条里占全部 30 条失败** |
| **判断先于生成，省一次调用** | 不该答的（议价/投诉/闲聊）**不用先生成再拦截**；顺带把"该答而资料没有"直接转人工，不做无用功 |
| **概率可直接当置信度用** | 判断返回概率；不需要像现在这样用检索分数硬凑置信度 |
| **判断调用比生成调用便宜一个量级** | 判断约 $0.00004/次，起草才是主要的钱 |
| **口径变成可校准的** | 题目是显式的 7~10 道；改题目 → 跑你的 600 条标注集 → 看命中率 / 打分题 MAE。**你现在改正则没有这种校准闭环** |
| **降级路径天然** | 判断超时/失败 → 退回现在的规则流水线（Jev 自己就是这么兜的），不会弄挂主链路 |
| **题目之间的一致性可以验证** | Jev 官方要求"题目不许互相矛盾"，并且有具体修法（收窄措辞、移除重叠维度）——这套方法论可以直接用 |

## 5. 风险（按严重程度排）

### 5.1 题目语域不对口 —— 最大工作量，也是最大失败点
「Jev 聊天助手」的 8 道题是为**社交沟通**设计的（平台是 QQ / X / 飞书，关系设定是
"恋人 / 朋友 / 同事 / 家人"，`true_intent` 的选项是"确认你在不在乎 / 发泄怒气 / 和平收尾"…，
群聊还明确说不准）。**直接照抄到客服用会错。** 必须按客服语域重写题目
（问价 / 问库存 / 问规则 / 议价 / 投诉 / 骚扰 / 无效），并**重建标注集**。
**没有标注集就调权重 = 拍脑袋**（这句话你自己文档里已经写过）。

### 5.2 隐私：多了一个固定的第三方端点 —— 对客服场景最致命
现在的隐私口径是"**资料和对话不出本机**，只把'客户这一句话 + 命中的资料片段'发给店主**自己配的**模型接口"。
接入 Jev 意味着**每条客户消息都要发到 TypeSafe / OpenRouter**。店主会问"我客户的消息发给谁了？"——
这一条不解决，功能再好也不该上。

**可选口径**：① 让店主自备 Jev key（他付钱、他知情）；② 只在**灰度**里跑（见 §6）。

### 5.3 成本结构变了
判断虽然便宜，但**每一条消息都要调一次**（包括"嗯""好的"这类）。
你现在的规则层是 **0 成本**。每天 100 条 × 30 天的口径要重算，别直接沿用 ≈¥12/月。

### 5.4 可解释性与调优速度下降
现在"该不该答"完全由**你写的词表**决定：可解释、可审计、**改一行即时生效**。
换成模型判断后，不达标**只能改题目措辞重跑**（Jev 自己的做法是"最多 3 轮"），
调优周期从**分钟级**变成**小时级**；而且出问题时你要解释"模型为什么判错"更难。

### 5.5 阈值不会消失
Jev 给概率，你还是得定"概率 > 多少才自动发"。
**所以不是"换了 Jev 就不用定阈值"，只是把"相似度阈值"换成"判断概率阈值"。**

### 5.6 判断与生成会打架
判断说"安全"，生成出来的话仍可能越权（Jev 自己踩过：`should_answer_now` 给 0.77、
`best_action` 却说"先翻聊天记录"，两题打架）。
**所以 §3 里的事后护栏（三类落地校验 + 承诺 + 拖延）一条都不能删**，它们要变成第二道。

## 6. 结论与建议路径

**结论：不要整体替换。只替换"该不该答 / 该不该发"这一个决策点。**

保留三样东西不动：
1. **本地规则前置**（无信息量 / 太短 / 时钟直答）——0 成本，没必要花钱
2. **事后护栏**（数字/型号/时间落地校验 + 越权承诺 + 拖延话术）——这是"答错"的最后一道
3. **阈值兜底**（检索分太低一律转人工）

### 建议的四步走（第一步做完就能决定要不要继续）

| 步骤 | 做什么 | 成功标准 |
|---|---|---|
| ① **写题 + 建标注集** | 按客服语域写 8~10 道题（是非 / 单选 / 打分），用**已有的 600 条评测数据**当标注集 | 题目之间不矛盾（自查一遍） |
| ② **影子模式（shadow）** | 判断结果**只落日志，不影响发送**，与现有规则层的决策逐条对比 | 判断层在你的标注集上，命中率／一致性**明显优于**现有规则 |
| ③ **灰度** | 只在"新问题类型"上启用（比如**只**用它决定"该不该答"），规则层继续兜底 | 危险直发仍为 **0**，且"该答没答"数量下降 |
| ④ 再评估要不要扩大 | 用同一套尺子（46 题 + 3×200 条）对比 | 两个指标不退化才扩大 |

**验收线**（照 Jev 自己的脚手架，但用你的数据重定）：
- 打分题：**平均绝对误差 < 1 档**
- 选择题（意图 / 该不该转人工）：**命中率 ≥ 60%**（客服场景建议提到 70%+，
  因为判错的代价比 Jev 那个场景高）
- 不达标 → 改题目措辞，最多 3 轮，每轮数字记进报告

### 面试时怎么讲这件事（这是最能体现 AI PM 判断力的一段）

> "我用检索相似度当'该不该答'的代理，跑完评测发现这是最弱的一环——600 条失败的 30 条全是
> **该答没答**，其中约 10 条就是分数卡在门槛附近。所以我看了一个专门做决策的模型 Jev：
> 它只回答选择题和打分、返回概率，不生成文字。
>
> 我**没有直接接**，理由有三个：一是它的题目是社交语域，客服要重写题目并重建标注集；
> 二是它会引入一个固定的第三方端点，和我'对话不出本机'的隐私口径冲突；
> 三是阈值不会因此消失，只是换了个对象。
>
> 我给自己定的路径是**先跑影子模式**——判断结果只落日志不影响发送，用我那 600 条标注集
> 对比它和现有规则层的决策，明显更好才灰度启用。**先证明它更好，再让它碰客户。**"

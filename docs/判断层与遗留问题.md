# 判断层与遗留问题报告（任务 3 + 任务 4）

**日期**：2026-09-24　**状态**：已上线并实测

## 任务 3：该不该答 判断层

### 做了什么

新增 `rag/judge.py`：在检索/生成**之前**先回答"这条消息需不需要回"。

| 情况 | 判断 | 行为 |
|---|---|---|
| 收尾/确认/感谢（谢谢、好的、收到、嗯嗯、没事了、再见…） | `should_reply=False` | 走新的 `no_reply` 档：**不回、不转人工、不弹窗、不发占位语**，只标记已见 |
| 明显是问题（含 吗/呢/？/怎么/什么/多少/有没有/多少钱/租/押金…） | `should_reply=True` | 照旧走检索 + guard 二档分流 |
| 拿不准 | `should_reply=True` | 宁可多回一句，不漏真问题 |

判断刻意保守：**短消息 + 全匹配收尾词 + 没有疑问信号**三条同时成立才判"无需回复"。

新增 dispatch 档位 `no_reply`，`main.py` 红点路径与兜底路径都显式处理
（`tests/test_judge_should_reply.py::test_no_reply_is_not_treated_as_escalation_in_source`
断言两条路径都在）。

### 解决的具体问题

机器人对着"谢谢/好的"又回一句"不客气，还有什么可以帮您" —— 检索分数再高也不该回；
而且这种回复会挤占扫描周期、还可能触发转人工占位语，变成刷屏。

### 测试

`tests/test_judge_should_reply.py` —— 48 个用例：
24 个收尾语必须判"不回"、15 个真问题必须判"要回"（含 `好的，那X-T5怎么租`
这种"以收尾词开头但其实是问题"的）、边界（超长消息、空消息、批量最后一句话是谢谢但前面有追问）、
以及"收尾语必须在 embedding/检索/LLM 之前就返回"（用 `Responder.__new__` 绕开网络与 Qdrant 验证）。

### 诚实说明：这一层没有"替代" 0.65 阈值

`top_score > 0.65 且 guard 不拦 → 直发` 这条门槛**保留**。judge 层加的是
"该不该答"这个**新维度**，不是把阈值换成模型打分。原因：

- Jev 那种"让模型答 7 道题再决定"的判断器，需要一套人工标注集 + 校准脚手架
  （它的 `tools/jev/calibrate.py` 就是干这个的，验收线 MAE<1.0 档、命中率≥60%，
  不达标就改措辞重跑）。没有标注集就调阈值/加权重，等于拍脑袋。
- 直接改阈值会立刻改变线上行为（更多或更少的转人工），而按客户实际语料校准之前
  没有证据说明往哪个方向调是对的。

想继续推进的话，正确的下一步是：攒 30~50 条真实客户消息 + 人工标注"该直发/该转人工"，
再照 jev 的脚手架评估，用数据决定要不要换成模型判断器。

## 任务 4：遗留问题

### 4.1 回复冷却改成按客户记

**问题**：`reply_cooldown_seconds: 30` 是**全局**的，而且兜底扫描整轮被它挡住 ——
给 A 回完话，同一个 30 秒窗口里 B 发来的消息会被完全跳过（多客户漏人）。

**改法**：
- `MessageDetector.mark_replied(customer_name=None)` / `is_in_cooldown(customer_name=None)`
  按客户分别记时间戳；不传名字时保持旧的全局语义（兼容）。
- `main.py` 兜底扫描不再用全局冷却挡整轮；改在 `_scan_fallback` 内部
  **只跳过"刚回过话的那个客户"**（`detector.is_in_cooldown(cust_key)`）。
- 红点路径的冷却检查也改成按客户。

**实测**（22:22:53 日志）：
```
兜底行0 y=129 对话名: [客户A@微信] 客户=True
兜底行0 客户A@微信 回复冷却中，跳过        ← A 刚回过，跳过
兜底行1 y=223 对话名: [客户D@微信 …] 客户=True   ← B 照常处理
```

`fallback_click_cooldown_seconds: 120` 保持不动：它已经带**行内容指纹**，
客户发新消息会改预览 → 指纹变 → 立即放行；没变才冷却，这是对的行为。

测试：`tests/test_reply_cooldown_per_customer.py`（6 个用例）。

### 4.2 PaddleOCR 崩溃 → 已换 RapidOCR（任务 2 完成）

`could not execute a primitive` 是 paddle 运行时的偶发崩溃（每半小时数次，一崩丢一轮扫描）。
任务 2 已把默认后端换成 RapidOCR/ONNX（`ocr.backend=rapidocr`），
并保留 `paddle` 作为可回退后端（`ocr_engine.py` 初始化失败会自动回退另一个）。

### 4.3 打包 spec 跟着换

`WeComBot.spec` 原来按 PaddleOCR 打包（`import paddle`、paddle DLL、paddleocr 的
tools/ppocr/ppstructure 数据目录）。已改为：

- 去掉 `paddle` / `paddleocr` 的 hidden imports、DLL 与数据目录
- 加 `rapidocr_onnxruntime` / `onnxruntime`，用
  `collect_data_files("rapidocr_onnxruntime")` 打进自带 PP-OCRv4 onnx 模型
  （det 4.5MB + rec 10.4MB + cls 0.6MB），用 `collect_dynamic_libs("onnxruntime")`
  打进 `onnxruntime.dll` 等
- `imageio` 的 dist-info 改成有就带、没有就跳过，spec 不再因为缺包直接炸

**已验证**（`PyInstaller.utils.hooks` 实际调用）：
```
rapidocr data files: 4
    \rapidocr_onnxruntime\models\ch_PP-OCRv4_rec_infer.onnx -> rapidocr_onnxruntime\models
    \rapidocr_onnxruntime\config.yaml -> rapidocr_onnxruntime
    \rapidocr_onnxruntime\models\ch_ppocr_mobile_v2.0_cls_infer.onnx -> rapidocr_onnxruntime\models
    \rapidocr_onnxruntime\models\ch_PP-OCRv4_det_infer.onnx -> rapidocr_onnxruntime\models
onnxruntime binaries: 2
    \onnxruntime\capi\onnxruntime.dll -> onnxruntime\capi
    \onnxruntime\capi\onnxruntime_providers_shared.dll -> onnxruntime\capi
```

顺带的好处：不再打包 ~2GB 的 paddle 运行时，包体会明显变小；也不再和 torch 抢 DLL。
测试：`tests/test_build.py::test_spec_no_longer_bundles_paddle`。

**自验缺口**：没有真跑一次 `python scripts/build.py`（全量 PyInstaller 打包很重，
本机原先连 PyInstaller 都没装）。只验证了 spec 语法与两个 collect_* 调用的真实输出。

### 4.4 顺手修掉的一个严重 bug（自己引入的）

换 PrintWindow 时给 `native_win` 的 Win32 函数设了 `argtypes`，结果用错了实例：

```
ctypes.windll.user32 是进程内共享单例，pywin32 用的就是它。
把 GetWindowRect.argtypes 设成 POINTER(wintypes.RECT) 之后，
win32gui.GetWindowRect 抛：
    TypeError: expected LP_RECT instance instead of pointer to RECT
```

后果：`scanner.get_region()` / 发送路径整体挂掉。日志里是
`[发送失败] 客户A@微信: argument 2: TypeError: ...`。

修法：`native_win.py` 改用**独立的** `ctypes.WinDLL("user32"/"gdi32"/"kernel32")` 实例
（argtypes 只作用于自己），`scripts/probe_capture_wework.py` 同步改。
加了两个回归测试：
`test_native_win_uses_private_dll_instances`、
`test_pywin32_getwindowrect_still_works_after_import`。

**实测确认修好**（22:25:39）：
```
转人工(兜底): 客户A@微信 - 检索低(0.32)
[发送] 客户A@微信: 帮您确认下这个授权码的事，稍等。     ← 发送成功，不再 TypeError
```

## 二、需求 1：提示词 + 资料库面板

### 1.1 提示词编辑

**做法**：把提示词**外置成文件**，首次运行从代码里的默认值生成：

```
prompts/
  system.md          业务回复的提示词
  smalltalk.md       闲聊提示词
  hold.md            占位语提示词
  tone_samples.md    口吻样本（一行一条）
```

读取优先级：`prompts/*.md` > 代码默认值。面板里改完写回文件，**保存后立即生效**（不用重启）。

**⚠️ 两个必须处理的坑**：

1. **占位符**：提示词里有 `{context}`、`{conversation_history}`、`{tone_samples}`。
   用户删掉它们 → 格式化时 KeyError → 程序崩。
   **对策**：保存前校验必须含哪些占位符，缺了直接拦住并提示。

2. **硬规则不能删**：现在的提示词里有"不许编造""用词必须确定""不透露是 AI"等安全规则。
   用户手一抖删了 → guard 会把大量回复拦成"需要人工处理"，用户会以为程序坏了。
   **对策**：面板分两块 ——
   - **可自由编辑区**（性格、风格、口吻、业务话术）
   - **受保护区**（安全规则，只读展示 + 一句"这些不能改，改了会答错"）

   比"全都可编辑"啰嗦，但能避免用户把自己搞崩。

3. 配「恢复默认」按钮 + 保存前预览（用一条真实客户消息试跑一遍看输出）。

### 1.2 资料库：上传 → AI 学习归纳

**支持的格式（分两批做）**：

| 批次 | 格式 | 依赖 | 风险 |
|---|---|---|---|
| 第一批 | txt / md / csv | 标准库 | 低 |
| 第二批 | docx / xlsx / pdf | `python-docx` / `openpyxl` / `pdfplumber` | 中（解析器各自会失败） |
| 第三批 | 图片（价目表照片）/ 网页 | 现有 RapidOCR / requests | 中 |

**每条解析器都要"部分成功"**：一个文件解析失败不能影响其它文件，失败的要单独列出来。

**AI 学习归纳**（这是最容易出事的一步）：

用户上传一份产品手册 → 让 LLM 抽成知识条目。**最大的风险是 LLM 编造**。

必须做的三件事：
1. **抽取时约束**："只从原文抽取，原文没有的数字/政策一律不写"。
2. **抽完让用户过目**：显示"从 X.pdf 抽到 12 条，其中 2 条含数字（高亮）"，用户点确认才入库。
   —— **不能自动入库**。一次编造的价格进了库，机器人就会一直报错价。
3. **保留出处**：每条知识带上 `来源=产品手册2026.pdf 第3页`。检索到它时能追，答错了能删。

**落盘**：抽取结果写成 `data/chat_raw/uploaded/<原文件名>.ta.txt`，和现有 KB 同格式，复用现有切块/嵌入流程。

### 1.3 一句话指令改资料库

例：「把日租 95 改成 98」「删掉关于无人机的内容」「加一条：周末不发货」

**做法**：把指令 + 相关资料条目喂给 LLM，让它输出**结构化操作**：

```json
{"ops": [
  {"action": "update", "match": "富士 X-T5 日租 95 元", "new": "富士 X-T5 日租 98 元"},
  {"action": "add", "text": "周末不发货，周一统一寄出"},
  {"action": "delete", "match": "无人机"}
]}
```

然后：
1. **显示 diff 让用户确认**（哪条改成什么、删了哪条、加了哪条）
2. 落盘（改 `data/chat_raw/*.txt`，或者维护一份 `data/kb_edits.json` 覆盖层）
3. **只重嵌入受影响的那几条**（Qdrant 支持按 id 删/upsert，不用全量重建）

**⚠️ 必须有**：确认 + 备份 + 撤销。LLM 误解指令改错资料是很常见的。

### 1.4 必备的配套：**「试问一句」**

一个输入框：输入客户问题 → 显示**检索到哪几条、分数多少**。
这是用户判断"资料改对没有"的**唯一可靠方式**。没有它，用户只能靠"给机器人发消息试试"，效率极低。

### 1.5 还需要一个「重建索引」按钮

把现在 `scripts/run_local.py --clean` 搬到 UI 上。上传/编辑后可能需要全量重建（尤其是改了切块逻辑）。

## 三、需求 2：从"人工编辑后发出"学习

**数据来源天然就有**：待人工队列里存着 **AI 草稿**，用户点「编辑」改完发出的就是**真实文本**。两者的 diff 就是最真实的偏好信号。

### 3.1 学语气（高价值、低风险）

- 每次「编辑后发出」→ 追加 `data/learned/tone_samples.jsonl`
  ```json
  {"at": "2026-09-25T01:30:00", "customer": "客户A", "ai_draft": "...", "sent": "...", "kind": "tone"}
  ```
- `build_tone_block()` 优先用**学到的样本**（最近的 N 条），不够再补内置样本
- **只学措辞，不学事实**：样本进提示词时明确标注"只学语气，事实仍以知识片段为准"

这是我编的那 13 条假样本的**正确替代品** —— 用你真实说过的话。

### 3.2 学资料（高价值、**高风险**）

用户的编辑有两种性质，**必须分开**：

| 编辑内容 | 性质 | 处理 |
|---|---|---|
| "帮您问下 X，稍等" → "稍等啊，我问下店里" | **改措辞** | 进语气样本，自动生效 |
| "日租 95" → "日租 98" | **改事实** | ⚠️ 这是**资料更新**，绝不能当语气学 |

**区分方法**：编辑后的文本里出现草稿里**没有的数字/型号/政策词**，就判为"疑似事实修正"。

处理：
- **不自动入库**，而是弹一句："这条看起来是资料更新（把 95 改成 98），要加进知识库吗？"
- 用户点「是」→ 走 1.3 那套（diff 确认 + 落盘 + 重嵌入）

**为什么必须人工确认**：如果用户某次紧急情况下随手改了个数字（比如临时报价），自动入库就把**一次性特例变成了永久政策**。

### 3.3 学习闭环的四条边界（这几条我会坚持）

1. **语气可以自动学，事实必须人工确认**
2. **给一个「学到了什么」页面**：列出所有学到的语气样本，能逐条删（用户可能说过一句不该学的）
3. **「这条别学」开关**：编辑框旁边一个勾，勾上就只发不学
4. **资料库可回滚**：每次修改留历史版本，能退回上一版

## 四、建议的分期（按风险，不按工作量）

### P0：低风险、见效快
1. 提示词外置 + 编辑面板（占位符校验 + 受保护区 + 恢复默认）
2. 口吻样本改成可编辑文本框（把假样本替换成真话）
3. 「试问一句」检索验证框

**这一批做完你已经能明显感觉到变化**，而且几乎没有搞坏资料库的可能。

### P1：中等风险
4. 待人工「编辑后发出」→ 追加语气样本（**只学语气**）
5. 资料库上传：**只支持 txt/md/csv**（纯文本，不走 LLM 抽取，直接切块入索引）
6. 上传文件的源文件保留 + 「重建索引」按钮

### P2：高风险，一项一项来
7. PDF / Word / Excel / 图片 解析
8. AI 抽取资料（**必须过目确认**）
9. 一句话指令改资料库（**diff 确认 + 备份 + 撤销**）
10. 编辑里的事实修正 → 提议更新资料库（**人工确认**）

**为什么不一次做完**：P2 每一项都能**污染知识库**。知识库一坏，机器人就开始报错价格 —— 这是客服场景里最不能出的错。所以每一步都要有"确认"和"撤销"，宁可多按两次按钮。

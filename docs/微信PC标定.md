## 三、这一路修掉的 5 个真 bug

| # | bug | 影响 | 修法 |
|---|---|---|---|
| 1 | `probe_my_color` 取"聊天区最常见的有彩色"当主题色 | 微信转账卡片/头像的橙色 `(253,206,157)` 像素比绿气泡还多 → 橙色被当成"我方颜色"，**绿气泡全判成对方，分边整个反了** | 改成 `learn_side_colors`：**按位置学**（我方靠右）学出颜色，再复核。右半边 `(157,242,159)×4`、左半边 `(238,238,240)×5`，距离 166 |
| 2 | `min_title_len=2` 默认值 | 微信标题就是两个字「微信」，`len("微信") > 2` 为假 → **窗口找不到** | `find_main_hwnd` 加 `prefer_title`；profile 里 `min_title_length=1` |
| 3 | 客户判定只有 `@微信` 后缀规则 | `@微信` 是"微信用户加了企业微信"才显示的，**微信客户端里根本没有** → 一个客户都判不出来，机器人安静地什么都不干 | 新增 `customer_match: "any"`（排除法）；profile 映射 `customers.name_rule` → `ocr.customer_match`；实测补齐排除词（`微信游戏` 一开始被误判成客户） |
| 4 | `_message_detector.py` 模块顶层 `from paddleocr import PaddleOCR` | 早就换成 RapidOCR 了，这行是死代码 + 崩溃源：连锁 import albumentations→torch，没先导 torch 的进程直接 `OSError WinError 127 torch/lib/shm.dll` | 改成懒加载（只留 `ocr` property 里）；现在单独 `import wxbot.detector` 不再需要先 import torch |
| 5 | 发送路径写死 `getWindowsWithTitle('企业微信')` | 切到微信模式后，发送会去激活**企业微信**、把回复粘进企业微信窗口 —— 现象是"微信一条没回，企业微信里莫名多了话" | 标题改成从 profile 读（`wecom.title_hint`）；`apply_to_config` 映射 `window.title_hint` |

第 4、5 条是通用的稳健性问题，跟微信无关 —— 尤其第 5 条，是在"能自动发"这条路上必须修的。

## 四、用户决策

* **群聊：不管了。** 现有规则是排除法（不是系统号就算客户），微信群会因此被当成客户。
  确实要拦的话，在 `profiles/wechat_pc.json` 的 `customers.exclude_keywords` 里加群名特征即可。
* **微信要能自动发。** 所以没给微信侧加"只填草稿不自动发"的限制，
  发送仍走 `_switch_to_wecom_and_back`（抢前台 + 剪贴板 + 回车）。
  **代价**：每次回复都会把微信切到前台再切回来，用户正在别的窗口打字会被打断。

## 五、没验到的

* **没有实发过消息。** 发送路径的窗口选择有单测（`tests/test_send_target_profile.py`），
  但"在微信 PC 上真的把字粘进输入框并回车"没跑过 —— 那会给真实联系人发消息。
  实机验证需要你同意，向某个联系人发一条测试消息。
* **群聊、公众号、小程序卡片**等特殊会话会被当成客户（用户已决定不管）。
* 微信窗口现在只占屏幕左半边（1458 宽）。窗口大小变了要不要重标定？
  布局是固定像素、不随窗口宽度变（和企业微信一致），但**上下边距**理论上跟着高度走 ——
  改过窗口高度建议跑一次 `--check`。
* `profiles/wechat_pc.json.template` 仍留在仓库里当"没装微信的机器"的说明；
  现在 `wechat_pc.json` 已存在，设置面板里「微信 PC · 截图模式」已自动可选
  （可选性按 profile 文件是否存在动态判定，不再写死）。

## 六、怎么切过去

设置面板 → 选「微信 PC · 截图模式」→ 保存 → 「立即重启」。
或直接改 `config.json`：`"channel": "screenshot"`、`"profile": "wechat_pc"`，重启。

回到企业微信：把 `profile` 改回 `wecom` 即可。

把朋友、群、营销号、新闻号全判成客户，一轮点开了 6 个会话（共 12 次，
点开会话＝清掉对方未读且不可逆），并自动发出一条占位语到一个群聊：

         兜底y=129 OCR: 离职 励志大礼包 是的 还有一些小物件 …在中南万象混口奋斗餐吃

只有 1 条发出去。用户在界面上看到"它点了很多我的其它对话框"。

### 四个叠加的根因

| # | 根因 | 证据 |
|---|---|---|
| 1 | 客户判定对企业微信之外的软件太宽（`customer_match=any` 排除法） | 日志里 6 行全是 `客户=True`，包括"腾讯新闻""微信游戏" |
| 2 | **行几何用的是企业微信的值** | 微信实测名字行首 `[139,240,336,435,534,628]`、行高≈98；config 是 `ratio=0.0747`（→129）+ 行高 94 → 偏移 `[-10,-17,-19,-24,-29,-29]`，第 5 行偏 29px 就跨到隔壁行 |
| 3 | 兜底扫描**找到第一个待回复客户后仍继续点**其余行 | 一轮 6 次点击；代码里注释写着"不 return …把剩下的客户行也过一遍" |
| 4 | 红点路径**没走白名单** | 复核时发现：白名单只加在兜底路径，红点路径是后门（微信红头像会被企微红点规则误判成未读） |

### 整改（决定 B：修到安全；决定 C：只进待人工）

| 项 | 改法 |
|---|---|
| 行几何进 profile | `layout.list_start_y_px=139`、`layout.row_height_px=98`；`_scan_fallback` 里**绝对像素优先、比例兜底** |
| 行裁剪范围可配 | `crop.name_row.x_from_ratio=0.20`（跳过头像列） |
| **客户白名单** | 新增 `wxbot/scan_policy.py`：`row_eligibility()` 纯函数；`customers.require_whitelist=true` + `whitelist=[]` → **空名单＝谁都不点**。微信侧出厂默认就是空的 |
| 两条路径都拦 | 白名单在 `_main_impl` 里算一次，红点路径与兜底路径共用；`click_col2_row` 之前判定 |
| 找到就停 | 兜底循环取到第一个待回复客户后 `break`（不再点完所有行） |
| 关掉红点 | `detection.red_dot.enabled=false`（微信个人号里红头像会被误判） |
| **仅人工模式（C）** | `dispatch.allow_auto_send=false` → `rag.allow_auto_send=false`；responder 里**连占位语都不发**，只推待人工 |
| OCR 防护 | `ocr_engine.extract_text` 对 0 尺寸图直接返回 `""`，resize 宽 `max(1,…)` |
| 顺带 | `pipeline/video_qa.py` 改用共享的 `resolve_config()`（原来自己读 `DEEPSEEK_API_KEY`，被设置面板清空后报"no key"） |

### 生效状态（实测启动日志）

```
已套用 profile: 微信PC（窗口类=Qt51514QWindowIcon，聊天区起点=462）
客户白名单已启用：（空 —— 不会点开任何会话）
```

再加上 `allow_auto_send=false`：**即使点了「开始」，它也不会点开任何会话、不会发任何消息**。
要让它干活，必须在 `profiles/wechat_pc.json` 的 `customers.whitelist` 里填上真实客户的会话名。

### 没验到的

* **没在真实微信上跑过"修好之后"的扫描** —— 那需要点界面上的「开始」，而我不想在没得到你确认前
  让它碰你的微信。启动日志只能证明"白名单已生效、名单为空"。
  白名单判定本身有纯函数测试覆盖全部分支。
* 白名单匹配用的是**会话名精确匹配**。OCR 名字可能有误差（实测出现过 `[大]` 这种）。
  建议把你列表里的名字原样抄进去，跑一次看日志里 `对话名: [...]` 是否与你填的一致。

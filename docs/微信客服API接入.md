---

**为什么是「微信客服」**：它是企业微信官方唯一一套能让程序**读到微信用户发来的消息、
并以客服身份回复**的接口（客户联系、会话存档都做不到"回复"）。
截图模式里的"客户"（会话名带 `@微信`），在 API 模式里就是 `external_userid`。

好处：不用开企业微信桌面端、不截图、不抢前台、不受 OCR 认错字影响。
代价：**必须先在后台把凭据配好**（见下），而且只能在客户发消息后 48 小时内回复。

## 一、拿凭据（都在微信客服后台）

**入口有两个，进哪个都行**：
* 直接开 <https://kf.weixin.qq.com/>（微信客服自己的控制台）
* 或：企业微信管理后台 →「应用管理」→「微信客服」

> ⚠️ **先记住这一条，能省你很多事**：我们的程序是**主动拉消息 + 主动发消息**
> （`sync_msg` / `send_msg`），**不用回调模式**。
> 所以后台那页上的「**回调URL / Token / EncodingAESKey**」**都不用填** ——
> 那三个是"微信把消息推给我们"才需要的，我们是自己去拉的。

要拿的只有三样 + 一样配置：

1. **企业 ID（corpId）**：后台的「企业信息」页，形如 `ww10123456789abc`
2. **客服账号 ID（open_kfid）**：「客服账号」列表里，形如 `wkxxxxxxxxxxxx`
3. **微信客服 Secret（corpSecret）**：「API」那一页
   ⚠️ 是**微信客服**这栏的 Secret，**不是**「自建应用」的。拿错了报 `40001`
4. **可信 IP**：同一页「API」→「可信 IP」，把**这台电脑的出口公网 IP** 加进去

### 查该填哪个 IP（这一步最容易错）

```bash
python scripts/wecom_api_selftest.py --ip
```

它会用**和机器人完全相同的那条直连**去查（绕开系统代理），所以查出来的才是对的。

2026-09-27 在本机查是 `203.0.113.10`。

两个坑：
* **不要用浏览器搜"我的 IP"的结果** —— 浏览器可能走代理，查出来的是代理出口 IP
  （实测这台机器走代理是 `203.0.113.10`，填进后台不认）
* 机器同时有 IPv6 时，程序查回来的可能是一串 `2409:...` —— 微信客服的可信 IP 要
  **IPv4**，所以代码优先查 IPv4
* **家宽/公司网重启后 IP 会变**，变了要回来重新加。报 `60020` 基本就是这个

### Secret 找不到怎么办（2026-09-27 实测记录）

微信客服后台那一页把 Secret 放在**「API」配置完成之后**：要你先填「接收消息服务器」
（回调 URL + Token + EncodingAESKey）→ 点「完成」→ 下一页才显示 Secret。
而**我们的程序不用回调模式**（自己拉消息），所以那个 URL 填了也没意义 ——
而且微信会去验证它，填假的过不了。

按这个顺序找/试：

1. 「API」页上找有没有单独的「**查看 Secret**」/「企业 Secret」入口
2. 「**企业信息**」页也找一下（有的版本放这儿）
3. 都找不到 → 用**自建应用的 Secret**：
   企业微信后台 →「应用管理」→「自建」→ 建/选一个应用 → 拿它的 Secret；
   再回微信客服后台 →「API」→ 把它设成「**可调用接口的应用**」；
   然后用这个 Secret 跑自检
4. 官方错误码查询工具（管理员登录后打开，会直接说原因）：
   <https://open.work.weixin.qq.com/devtool/query?e=40001>

**怎么判断哪个错**（自检会直接说，不用记）：

| errcode | 意思 | 怎么办 |
|---|---|---|
| `40013` | **企业 ID 不对** | 检查 WECOM_CORP_ID |
| `40001` | **Secret 不对**（企业 ID 是好的） | 换 Secret 试 |
| `60020` | 调用方 IP 不在可信 IP 里 | 用 `--ip` 查出来加进去 |
| `48002` / `60011` | 这个 Secret 没微信客服权限 | 去「API」把它设成「可调用接口的应用」 |

试候选 Secret 时不用先写进配置：

```bash
python scripts/wecom_api_selftest.py --corp-id ww.... --secret 候选值 --open-kfid kf....
```

**客服账号 ID 以接口返回的为准**：后台界面上显示的"账号ID"不一定是 `open_kfid`
（实测有人拿到 `kf...` 开头的一串，而接口要的是 `wk...` 开头的）。
Secret 一通，`account/list` 就会把**真正该填的值连同客服账号名字**打出来：

```
✗ WECOM_OPEN_KFID=wf... 不在你的客服账号列表里。
  **该填的是**：wkAJ2GCAAASSm4_FhToWMFea0xAFfd3Q（摄影器材租赁客服）
```

## 二、填进去（不用改代码、不用碰 .env）

主界面 →「设置」→ 软件选 **「企业微信 · API 模式」** → 填那三个框 →
点 **「测试企业微信连接」** → 通过后「保存」。

保存会写进 `.env`（`WECOM_CORP_ID` / `WECOM_KF_SECRET` / `WECOM_OPEN_KFID`），
并把 `config.json` 的 `channel` 切成 `wecom_api`。**换通道要重启**，点「立即重启」。

> ⚠️ **别只把 `.env.example` 复制成 `.env` 就以为配好了** —— 里面是
> `your_corp_id` 这种占位符。自检现在会直接指出来："还是 .env.example 里的占位符"。

命令行自检（等价于那个按钮，但结论更细）：

```bash
python scripts/wecom_api_selftest.py
```

它会逐个字段告诉你哪个填错、哪个 IP 没加（报 60020 时**直接告诉你此刻该填哪个 IP**），
而且**不会吃掉客户消息**（临时存/还原游标 —— 这个坑真踩过：自检把第一条真实消息永久跳过了）。

## 三、功能说明

| 消息 | 怎么处理 |
|---|---|
| 文字 | 走同一套 RAG + guard + 三档分流（和截图模式**完全一致**，共用同一个 responder） |
| 语音 | 请求服务端**转文字**（`voice_format=1`）；转出来就当普通问题回答，转不出来才应答"听不清，麻烦打字" |
| 图片 / 文件 / 视频 / 位置 | 回一句得体的话（模板可改）+ **转人工**，待人工里写清"客户发来图片，请到后台查看" |
| 客户进入会话 | 自动发**欢迎语**（走 `send_msg_on_event`，用事件里的 `code`） |

**连发多条只回一次**：一次拉取里同一客户的多条非文本消息会合并处理
（客户连发 3 张图 → 一句应答 + 一条待人工），不会刷屏。

分流策略写在 `gateway/api_policy.py` 里而不是 main.py 的闭包中 ——
当初就是为了能测才抽出来的（`dispatch_api_message` / `dispatch_api_nontext` /
`should_welcome` 都是纯逻辑 + 注入队列，不碰网络、不碰 GUI）。

### 可编辑的文案（知识库 → 提示词）

| 提示词 | 用在哪 |
|---|---|
| 欢迎语 | 客户进入会话时发的那句 |
| 非文本应答 | 图片/语音/文件… 各回一句，格式 `类型：话`，一行一条，认不出的类型落到「其它」 |

这两句**故意不过 LLM** —— 它们本来就该固定、可控、改完立即生效，
而且多发一次 LLM 调用就多等 1~2 秒。

### 发送失败会重试

`send_text` / `send_welcome` 默认重试 3 次（间隔 0.8s、1.6s）。
**参数或权限类错误不重试**（`40003` 用户不存在、`40001/40013` 凭据错、
`60020` IP 不在白名单…），因为重试也不会好，只是白等还可能触发频率限制。

## 四、欢迎语（两种模式都做，方式不同）

`config.json` → `welcome`：

| 键 | 作用 |
|---|---|
| `on_enter_session` | **API 模式**：收到 `enter_session` 事件就欢迎（**客户还没说话**就能招呼）。截图模式做不到这个 —— 客户不发言，屏幕上没有变化，这个动作不可观测 |
| `on_first_contact` | **两种模式通用**：第一次要跟某个客户说话之前，先招呼一句。截图模式靠它；API 模式如果没赶上 enter_session（比如程序是中途启动的）也靠它兜底 |
| `cooldown_seconds` | API 模式：同一个人多久内只招呼一次（默认 6 小时）。`enter_session` 会**反复触发**（客户来回切会话就会），不拦就会一直弹"在的～想租什么" |

文案在「知识库 → 提示词 → 欢迎语」。

**两种模式共用一份"招呼过"记录**（`data/state/greeted.json`）：API 模式发过
enter_session 欢迎语的人，第一次回复时**不会**再被招呼一遍。名字归一按
"是不是同一个人"（OCR 名字变体也算同一个），否则同一个人会被反复招呼。

截图模式发招呼的时机：发送队列里第一次要给某个客户发东西时，先发招呼，
正文**放回队列下一轮**再发（一次 tick 只发一条，不让界面一次卡两倍时间）。
招呼没发出去也照发正文，且本进程内不再重试（免得刷屏）。

## 五、已知限制与取舍

* **48 小时窗口**：只能在客户发消息后 48 小时内回复。待人工队列 24 小时过期，
  刚好在窗口内 —— 所以别把待人工压太久。
* **非文本消息看不到内容**：接口只给 `media_id`，我们的界面显示不了图片。
  待人工里只能提示"请到微信客服后台查看"。
* **游标是"拿到就推进"**：`sync_msg` 一返回就把书签落盘。
  如果这中间程序崩了/被关了，那批消息**不会再拉回来**（客户白问，日志也看不出）。
  要彻底解决得改成"处理完再推进"或持久化已处理的 msgid —— 目前没做。
* **去重按 msgid 且只在内存**：配合游标一般够用；重启后游标已推进，不会重复处理。

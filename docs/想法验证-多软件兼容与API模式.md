# 想法验证：多软件兼容（截图模式）+ API 模式

**验证日期**：2026-09-24　**结论**：**方向成立，但"用户手动截图就能适配任意软件"要打一个折扣** —— 颜色规则能通用，**几何/区域规则不能自动学**，必须让用户框选。

验证方式：在企业微信真实窗口上跑 4 个探针（`scripts/probe_universal_side.py`、
`scripts/probe_window_picker.py`，以及本会话前一轮的 `probe_capture_wework.py`、
`probe_click_postmessage.py`），并把现有代码里"跟 App 绑死"的部分逐条数出来。

---

## 一、拆开这个想法，逐条验

想法 =「同一套内核 + 每个软件一个 profile + 两种通道（截图 / API）」。内核部分是
"抓窗口 → 认消息 → 认谁说的 → 认新消息 → RAG 回复 → 发送"。逐条实测：

### H2「谁说的能靠颜色通用地分开」—— **成立** ✅

用 jev 的判据（框内底色众数占比 < 0.45 判为图片里的字；底色是主题色→我方；
对底色对比度 ≥150→对方；否则灰字）在真实企微截图上跑：

```
me     bg=(201,231,255) 众数占比=0.68   '帮您问下缺不缺保安，稍等。'   ← 我方蓝气泡
other  bg=(228,231,235) 众数占比=0.76   '你好'
other  bg=(228,231,235) 众数占比=0.69   '缺保安吗'
gray   bg=(245,247,250) 众数占比=0.74   '21:00'                      ← 时间戳被正确归到灰字
gray   bg=(245,247,250) 众数占比=0.70   '你已添加了客户D，现在可以开始聊天了。'
```

我方 / 对方 / 时间戳三类分得干干净净，**没有用到任何企业微信专属规则**。
这一条是"通用截图模式"最关键的技术假设，成立。

（过程中踩了个坑：第一版把 RGB 通道名写反了（`b,g,r = bg[0],bg[1],bg[2]`），
结果自己的蓝气泡全判成对方、`me: 0`。改过来才对。这条也说明**颜色规则的实现细节很脆**，
需要真机回归测试，不能只靠推理。）

### H3「输入框能自动定位」—— **成立** ✅

"面板 45% 高度以下第一根整行单色且非底色的分隔线"：

```
H3 输入框顶 y=1588（面板高 1728，占 92%）
```

和实际布局吻合（输入框就在最下面一条）。通用规则有效。

### H4「新消息能靠行像素变化发现」—— **成立** ✅（本会话已证）

不依赖任何 App 的红点规则：会话列表某一行的像素变了 = 这行有新内容。
本会话已验证这个机制在企微上工作（行指纹 + 内容变化绕过冷却 + `col2_seen`），
而且它是**纯像素**的，天生跨 App。

**但有个坑**：现在的实现靠"只取行宽的 72%"来排除时间戳列（"刚刚→1分钟前"会自己变）。
用户自己框选的行区域如果不避开时间戳，就会每分钟误判一次新消息。
通用版要么在向导里提示"框到时间戳左边为止"，要么把比对改成"只比 OCR 出来的文字"。

### H1「消息区能自动定位」—— **部分失败** ⚠️

jev 那套像素锚点（底色众数 + 左右边界 + 上下边界）在同一张图上：

```
H1 像素锚点: 面板底色=(245,247,250) 面板=(465, 0, 2019, 1728)
```

期望是"消息列表那一块"，实际拿到的是**整个中间列**，两个问题：

1. **纵向没有界**（y 从 0 到 1728）：企微顶栏、输入区、聊天区的底色是同一个，
   整行单色只出现在分隔线上，所以那套 `row > 0.9` 的判据失效。
2. **横向吃进了右侧 AI 侧边栏**（x1=2019，实际聊天列只到 ~1479）。
   结果 OCR 把侧边栏的 UI 文字全捞进来了：

```
gray  '客户需求'  '客户意向'  '成交卡点'  '服务建议'  '待办事项'  '跟进纪要'
gray  '企业名片'  '发起收款客户转账'  '直播'  '推荐客服'  '快捷回复'  '商品图册'  '客户详情'
other '服务总结'  '快速会议'  '··目···'  'B'
```

**这就是"通用"最真实的边界**：颜色规则能通用，**区域规则不能自动学**。
每个软件的侧边栏、工具栏、公告条位置都不一样，而这些东西的 OCR 结果会直接污染
"客户说了什么"。jev 自己的选择也是——**一个 App 一个适配器**，不搞万能自动适配。

**结论**：区域必须由用户提供（框选），或者由我们为已支持软件内置。

### 「用户点一下就能认出这个软件」—— **成立** ✅

`GetCursorPos + WindowFromPoint + GetAncestor(GA_ROOT)` 能直接拾取 profile 三要素：

```
直接描述企业微信句柄 394116：
    process      = 'WXWork.exe'
    window_class = 'WeWorkWindow'
    title        = '企业微信'
    title_length = 4
    rect         = [0, 0, 2019, 1728]
```

用户向导只要说"把鼠标移到你的聊天软件窗口上，停 2 秒"，我们就能自动填好这三项。

**但必须让用户确认**：实测自测时把鼠标放在"企微窗口中心"，拾取到的是 **Chrome**
（因为企微被 Chrome 挡住了，`WindowFromPoint` 返回的是最上层窗口）。
所以向导要显示"拾取到：企业微信（WXWork.exe）"让用户点头，而不是默认相信。

### 「不抢前台」—— **成立** ✅（前一轮已证）

PrintWindow 后台抓窗口（nonblack_ratio 0.9961）+ PostMessage 后台点击切会话。
这两条是"挂机跑、不打扰用户"的前提，已经上线。

## 二、API 模式：覆盖面比想象中窄

| 目标 | 官方 API | 说明 |
|---|---|---|
| 企业微信 · 微信客服 | ✅ 有 | 官方有「接收消息和事件」与「发送消息」文档（[接收消息和事件](https://developer.work.weixin.qq.com/document/path/94670)、[发送消息](https://developer.work.weixin.qq.com/document/path/96427)）。需要企业微信管理后台配置 + 回调地址。具体权限/额度要你在后台确认。 |
| 企业微信 · 会话内容存档 | ✅ 有，但要资质 | 拉取全量聊天记录，需企业认证 + 付费许可，本质是合规审计能力 |
| 个人微信 | ❌ 无官方 API | 市面上的"微信机器人"都是 hook / 协议逆向，违反用户协议、有封号风险 |

**所以 API 模式不是"覆盖所有软件"，而是"覆盖有官方接口的那几个"** ——
实际就是企业微信系 + 飞书/钉钉这类企业 IM。而**恰恰是这些软件，也正是截图模式最不想碰的**
（有接口就不该截图）。

**好消息**：API 模式和截图模式能共用同一套内核。现在的
`Responder.handle_customer_message(客户名, [消息])` 是通道无关的，RAG/guard/待人工队列/发送队列
都不用改，API 只是换掉"读消息"和"发消息"两头。这是这次重构里最干净的一块。

## 三、离这个产品还有多远（数出来的，不是估的）

现有代码里"跟企业微信绑死"的地方，**逻辑层面只有 4 处**：

| 位置 | 内容 | 处理 |
|---|---|---|
| `scanner.py:526` | `pyautogui.getWindowsWithTitle('企业微信')` | 改成读 profile 的窗口匹配规则 |
| `customer_id.py` | `@微信` 后缀 = 客户判定 | **这是业务规则不是 UI 规则**，必须让用户配（"哪些会话算客户"） |
| `wxbot/detector/red_dot.py` | 企微未读红点 | 通用模式改用"行像素变化"（已有） |
| `wxbot/detector/bubble.py` | 企微灰/蓝气泡配色 | 换成上面已验证的颜色规则 |

**几何参数已经全在 `config.json` 里**（`wecom` / `columns` / `crop` / `detection` /
`fallback` / `dedup` / `ocr`），所以"config → profile"这一步是**搬家**，不是重写。

**要新写的**：profile 存储与切换、窗口拾取向导、矩形框选向导（3~4 个矩形）、
通道抽象（`ScreenshotChannel` / `ApiChannel`）、内置微信 PC profile（**需要装了微信 PC 的机器实机标定**，
这台机器上没装，我验不了）。

## 四、我建议的改法（跟你原来的想法差在哪）

你原话是"用户也可以根据指示手动截图添加并命名软件"。
实测下来，**"截图"不够，要改成"框选"**：

| 你的想法 | 建议 | 为什么 |
|---|---|---|
| 用户手动截图 | 用户**框选 3~4 个矩形**：①会话列表 ②聊天消息区 ③输入框（发送按钮不用框，回车即可） | H1 实测：区域没法自动学；侧边栏/工具栏会污染消息 |
| 命名软件保存本地 | 同一件事，另存为 `profiles/<名字>.json` | —— |
| （未提） | 加一步"点一下窗口"自动填进程名/窗口类 | 已验证可拾取 |
| （未提） | 加一步"我方气泡是什么颜色"（默认自动探测，可手动覆盖） | 颜色规则通用，但主题色深浅不一，留个覆盖口 |
| （未提） | 加一步"哪些会话算客户"（如 `@微信` 后缀 / 全部 / 关键词排除） | `@微信` 是业务规则，不能写死在代码里 |

向导做完可以立刻自检：抓一帧、按用户框的矩形裁出来、把识别到的"对方说的话"显示给用户看，
用户点"对/不对"就完成标定。**这一条是这个产品能不能被普通用户用起来的关键**——
没有自检，用户框错了也不知道，只会觉得"这软件根本没用"。

## 五、风险（必须让你先知道）

1. **合规/风控**：截图模式对微信 PC 属于自动化操作，微信的用户协议不欢迎；企业微信宽松些
   （我们是辅助客服，不是群发）。要规模用，优先推 API 模式。
2. **"兼容所有软件"的真实成本不是 0**：每个软件仍然要人标定一次（内置的我们标，用户的他们标），
   而且软件改版（比如企微把侧边栏挪个位置）会打破 profile —— 需要"profile 失效检测"
   （本会话已经做了雏形：`check_layout` 像素锚点自检）。
3. **发送那一路仍然要抢前台**（Ctrl+V / Enter 需要键盘焦点）。截图模式做不到"完全无感发送"。
4. **API 模式要跑一个回调服务**（企业微信推消息给你），这跟现在这个单机 exe 的形态不一样，
   需要一个常驻的 HTTP 端点或内网穿透。

## 六、分阶段建议

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P0 | config → `profiles/` 结构化 + 启动时选 profile（内置"企业微信"） | 纯搬家，风险低 |
| P1 | 窗口拾取向导 + 矩形框选向导 + **框完立刻自检预览** | P0 |
| P2 | 把 `red_dot`/`bubble` 换成通用规则（颜色分边 + 行变化），企微 profile 作为默认参数 | P1，需真机回归 |
| P3 | `ApiChannel`（企业微信微信客服 `sync_msg`/`send_msg`）+ 回调服务 | 需要你的企业微信后台权限 |
| P4 | 内置微信 PC profile | **需要一台装了微信 PC 的机器实机标定**，这台机器没有 |

P0~P2 是把现在的代码变成"多软件产品"；P3 是换一条更稳的路；P4 是补一个高频目标。

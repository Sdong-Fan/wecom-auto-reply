### 2. 点会话不抢前台（PostMessage）

全程窗口不是前台、真实光标不动。`click_col2_row` 现在走这条。

### 3. OCR 换引擎
同一张真实截图（会话列表 364×1728、聊天区 950×1388）：

| | 行数 | 冷启动 | 热 |
|---|---|---|---|
| RapidOCR | 28 / 8 | 804ms / 671ms | **307ms / 356ms** |
| PaddleOCR | 33 / 8 | 735ms / 369ms | 343ms / — |

- 文本一致，甚至更干净：Paddle 把"星期二"误拆成"星"+"1"，RapidOCR 没拆错。
- RapidOCR 没有 paddle 运行时 → 不再有 `could not execute a primitive` 崩溃，
  也没有 torch DLL 冲突，日志不再吐整段 `Namespace(...)` DEBUG。
- 启动 195ms（`Loading RapidOCR` → `RapidOCR ready`），PaddleOCR 要 500ms+。

## 附带发现（都验证过）

- **`col2_seen` 去重现在真正生效了**：旧代码靠 mss 截屏，光标被画进图里 → 每帧都不一样 →
  兜底扫描每 1~3 秒空转一遍。换成 PrintWindow 后画面像素级稳定 → 列表没变就早退，
  日志会"安静"（这不是卡死，是省活了；点一下会话列表，日志立刻恢复）。
  早退是安全的：新消息必然改变列表预览/时间戳/未读角标 → 列表图变 → 正常扫。

## 没做 / 已知风险

- **发送那一路仍抢前台**：Ctrl+V / Enter 需要键盘焦点，`_switch_to_wecom_and_back`
  没动。只有扫描/点击会话变后台了。
- **PrintWindow 是同步跨进程调用**：正常情况下 ~15ms；万一企业微信 UI 线程卡死，
  PrintWindow 会跟着卡住扫描线程（不卡 GUI，因为扫描本来就在 daemon 线程）。
  后果和"一次慢 OCR"一样：扫描暂停，直到企微恢复或重启程序。旧 mss 没有这个风险，
  但旧方案有抢前台+光标漂移+截进自己 GUI 三个更频繁的问题。先记录，不预加看门狗。
- **最小化未在真实最小化状态下验过**（`ensure_renderable` 只测了逻辑）。
- **OCR 换引擎后，打包（PyInstaller）仍需改**：`scripts/build.py` 现在还是按 PaddleOCR
  打包 DLL；源码运行（启动.bat）不受影响。任务 4 一起处理。
- **OCR 子进程不需要**：扫描跑在 `threading.Thread(target=_run_scan)` 后台线程，
  Tk 主循环不受 OCR 阻塞（py-spy dump 确认主线程停在 `mainloop`）。jev 的
  "OCR 挪子进程"是因为它的 OCR 在 Qt 主线程里，我们没这个问题。
- **颜色分边**：现有灰/蓝气泡检测工作正常、无现场证据需要换，按"没坏就别动"跳过；
  jev 那套"底色众数占比 + 对比度阈值"留作以后气泡误判时的备选。
